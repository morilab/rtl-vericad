# アーキテクチャ

## 目的
本書は、単体ブラウザアプリと VS Code 拡張 WebView の両方を見据えた 2D CAD の基本アーキテクチャ方針を整理する。

## アーキテクチャ目標
- 早期フェーズでは単体ブラウザアプリとして素早く検証できること
- Cursor Cloud 等のクラウド環境でも、拡張梱包なしで単体アプリとして検証できること（ホスト差分を薄く保つ前提）
- 最終的に VS Code 拡張 WebView 上へ無理なく移行できること
- CAD の振る舞いを React から独立させること
- 実行環境依存の差分を明確な境界に隔離すること
- MVP の先に機能拡張しても全面的な作り直しを避けられること
- 表示系は可能な限り「与えられた状態を描画するだけ」に寄せ、ルール・編集ロジックを描画層に持ち込まないこと
- VS Code 拡張側および WebView 周辺の層は極限まで薄くし、ブートストラップと I/O 橋渡しに留めること

## オニオン構造（層の重なり方）
本プロジェクトは、依存の向きを内側へ向けるオニオン型の層構造とする。外側は内側の型・契約に依存し、内側は外側を知らない。

### 内側からの概要
1. **CAD コア（最内）**  
   ドキュメント、幾何、コマンド、履歴などの純粋なドメイン。描画 API・React・ホスト API に依存しない。
2. **アプリ UI**  
   画面の状態表示と入力の受け口。ルールの正はコアに置き、UI はコアへの問い合わせ・購読に徹する。描画コンポーネントは、コアまたは UI が組み立てた「描画用の見え方」（ビューモデル）を受け取り、可能な限り描画のみを行う。
3. **ホストアダプター（最外）**  
   ブラウザ単体・WebView 等の差分のみを吸収する薄い殻。永続化や通知など、環境が提供する I/O を共通インターフェースへ写すだけに近づける。

### この構造が単体検証と薄いホストに効く理由
- コアと UI の大半は、VS Code の有無に関わらず同一コードパスで動かせる。
- クラウド上ではブラウザアダプターだけで完結し、拡張のビルドや API 調整を検証の前提にしなくてよい。
- 拡張側にドメインや描画の重い処理を置かない設計を強制し、WebView 層の厚みを抑えられる。

## 想定する上位構成

### 1. CAD コア
責務:
- ドキュメントモデル
- エンティティ定義
- 幾何計算
- 選択ロジック
- スナップロジック
- 編集コマンド
- Undo/Redo 履歴

制約:
- React に依存しない
- VS Code API に依存しない
- 描画実装に依存しない

### 2. アプリ UI
責務:
- React コンポーネント
- ツールバー
- プロパティ表示
- レイヤ表示
- キーボードショートカット接続
- ポインタイベントの受け口
- キャンバス等による図面の表示（入力はコアまたは明確なコントローラ経由）

制約:
- CAD ルールそのものを直接持ち込まない
- CAD コアへ問い合わせる形を基本とする
- ホスト API は定義済みの境界経由でのみ利用する
- 描画は「表示専用」に近づける。クリック解釈やスナップ判定などのルールはコア側に置き、UI は結果の反映とイベントの転送に徹する

### 3. ホストアダプター
責務:
- 単体ブラウザ環境との接続
- VS Code WebView 環境との接続
- 永続化の橋渡し
- 通知や設定の橋渡し
- メッセージ送受信

制約:
- 実行環境固有の処理を上位へ漏らさない
- VS Code API の利用をホストアダプター内に閉じ込める
- 実装は極力薄くする。拡張ホスト側は WebView の起動、セキュリティ設定、メッセージの中継、ファイル連携の委譲など最小限に留め、CAD の意味論はすべて WebView 内のコア/UI に置く

## 状態分離方針

### ドキュメント状態
永続的な図面内容を表す。

例:
- エンティティ
- レイヤ
- メタデータ

### ビュー状態
図面をどのように見ているかを表す。

例:
- ズーム倍率
- パン位置
- ビューポートサイズ
- 一時オーバーレイ

### ツール状態
現在の操作モードと途中状態を表す。

例:
- 現在ツール
- 作図途中のドラフト
- スナップ候補
- ドラッグ中の起点

## 描画方式の方向性
現時点では、描画方式は Canvas 系を第一候補とする。

理由:
- CAD 的なパン、ズーム、再描画に向いている
- SVG より大量図形時の負荷を抑えやすい
- 早期に GPU 前提の複雑な構成へ入らずに済む

ただし、これは現時点の仮説であり、最終決定ではない。

## ホスト境界の考え方
UI は、ブラウザ専用 API や VS Code 専用 API を直接呼ばず、共通のホストインターフェースに依存する。

ホストの責務候補:
- ドキュメント保存要求
- ドキュメント読込要求
- ユーザー通知
- 設定取得と保存
- クリップボード連携
- メッセージ受信

## 履歴モデル方針
Undo/Redo を後付けにしないため、すべての編集操作は履歴管理可能な単位で扱う。

候補:
- コマンド指向
- 操作差分指向
- 限定的スナップショット指向

現時点では、コマンドまたは操作差分ベースを有力候補とする。

## 主な設計リスク
- React コンポーネントの内部に CAD ロジックを埋め込むこと
- 永続化形式を内部モデルと同一視しすぎること
- UI コードの各所から VS Code API を直接呼ぶこと
- WebView 制約と相性の悪い依存関係を無計画に導入すること
