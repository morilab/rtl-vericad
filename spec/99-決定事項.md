## 合意済み事項

| ID | 決定 | 理由 | 状態 |
|---|---|---|---|
| D-001 | 最終目標は VS Code 拡張の WebView 上で動作する 2D CAD とする。 | 開発者向けワークフローとの統合価値が高いため。 | 合意済み |
| D-002 | 初期フェーズでは、単体ブラウザアプリとして設計検証、操作性検証、デバッグを行う。 | 拡張機能パッケージ化の負担を避けつつ、CAD 特有の設計と操作性を早く検証できるため。 | 合意済み |
| D-003 | 現在は使用検討・仕様策定フェーズとし、明示的な承認がない限り製品実装は行わない。 | 要件と設計制約を先に固める必要があるため。 | 合意済み |
| D-004 | 仕様書、コメント、UI 文言は原則として日本語で記述する。 | レビューと合意形成を日本語中心で円滑に行うため。 | 合意済み |
| D-005 | `spec/` 配下のファイル名は、明確な理由がない限り日本語とする。<br>`spec/` 配下以外では、日本語ファイル名を禁止する。 | 設計文書は可読性を優先し、実装領域はツール互換性と運用安定性を優先するため。 | 合意済み |
| D-006 | `spec/05-VSCode連携.md` は混在名を許可する。 | VS Code は製品固有名として認知されており、日本語題名の可読性と対象範囲の明確さを両立しやすいため。 | 合意済み |
| D-007 | コミットメッセージは原則として日本語で記述する。 | 履歴レビュー時の文脈共有を日本語中心で統一し、仕様策定フェーズの判断経緯を追いやすくするため。 | 合意済み |
| D-008 | O-001「MVP に含める図形の範囲」は `spec/01-要件.md` の記述を決定事項として従う。 | `spec/01-要件.md` に MVP 図形と制約が具体化したため。 | 合意済み |
| D-009 | O-002「操作感」は CAD 寄りとする。 | 早期に操作方針を固定し、UI/ツール設計を収束させるため。 | 合意済み |
| D-010 | O-003「レイヤ」は描画の構成として定義するが、ユーザー向けレイヤ機能は MVP に含めない。 | MVP の操作を単純化し、内部設計と UI を分離するため。 | 合意済み |
| D-011 | O-004「座標の単位」は設けない（単位なし）。 | MVP ではオングリッド前提であり、単位系を固定せずに検証を進めるため。 | 合意済み |
| D-012 | 保存形式は内部・外部ともに JSON とする。 | 初期フェーズでは保存/読込を単純化し、WebView 移行時も host adapter 経由で扱いやすくするため。 | 合意済み |
| D-013 | アーキテクチャはオニオン構造とし、依存の正は内側（CAD コア）に置く。VS Code 拡張および WebView 周辺は極限まで薄くし、ブートストラップと I/O 橋渡しに近づける。 | クラウド等での単体ブラウザ検証を主戦場にできるようにし、ホスト差分のコストを抑えるため。 | 合意済み |
| D-014 | 図面の表示は可能な限り「表示するだけ」に寄せ、ルール・編集ロジックを描画層に持ち込まない。 | 表示とドメインの境界を明確にし、WebView と単体ブラウザで同じ検証対象にするため。 | 合意済み |
| D-015 | Cursor Cloud 等での単体検証可能性を重要な制約とする。検証の主戦場はコア、UI、ブラウザ用 host adapter とする。 | 拡張梱包なしで反復検証できる導線を確保するため。 | 合意済み |
