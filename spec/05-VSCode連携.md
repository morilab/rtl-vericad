# VS Code 連携

## 目的
本書は、最終目標である VS Code 拡張 WebView への統合に向けて、現時点から守るべき前提条件と設計制約を整理する。

## 前提
- 最終配置先は VS Code 拡張の WebView とする。
- 初期開発では単体ブラウザアプリで設計検証と操作検証を行う。
- 単体ブラウザ版と WebView 版は、可能な限り同じ CAD コアと UI 構造を共有する。
- Cursor Cloud 等のクラウド環境では、拡張を梱包せずに単体ブラウザアプリだけで検証できることが重要である。検証の主戦場は常に「コア + UI + ブラウザ用ホストアダプター」とする。
- VS Code 拡張側および WebView 周辺の層は極限まで薄くする。拡張は WebView の提供、メッセージ中継、必要ならワークスペース連携までに留め、CAD のルールや描画の重い処理は WebView 内のオニオン内側（コアと UI）に置く。

## WebView を前提とした制約
- UI はブラウザ互換環境で動作することを前提とする。
- 通常のフロントエンドコードから Node.js API を直接利用しない。
- VS Code 固有 API は host adapter 層に閉じ込める。
- ホストとの通信は明示的なメッセージ境界を持つ。
- ローカルファイルシステムへの直接アクセスを UI の前提にしない。

## ホストアダプタの責務候補
- 文書を開く要求の受け渡し
- 文書を保存する要求の受け渡し
- 設定の読み書き
- 通知表示
- クリップボード連携
- 拡張機能本体とのメッセージ交換

WebView 用ホストアダプターは上記を「環境 API とアプリ契約の間の薄い写像」に留めることを目標とする。ドメイン処理をホスト側に増やさない。

## メッセージ橋渡し方針
- request/response 形式のやり取りを基本候補とする。
- 通知系イベントは別経路またはイベント種別で区別する。
- メッセージ種別は型または仕様書で明確化する。
- CAD コアはメッセージ詳細を知らない構造とする。

## 永続化方針
- WebView 側は制限のないファイルアクセスを前提にしない。
- 永続化は host adapter と拡張機能側の責務分担で吸収する。
- 内部形式は JSON first を原則とし、ホスト固有処理はその外側に置く。

## セキュリティ・運用上の考慮
- CSP 制約を意識した構成にする。
- リソース読み込み経路を安易に固定化しない。
- ホスト境界を越えるデータは明示的に定義する。
- WebView で動かない前提の依存導入は避ける。

## 避けるべき設計
- React コンポーネント内で VS Code API を直接呼ぶ設計
- UI から `fs` や `path` に依存する設計
- 保存処理を描画やツール状態に埋め込む設計
- ブラウザ単体版でしか成立しない前提を持つ設計
